# Academia — Modelagem física (Sprint 3)

Implementação PostgreSQL do modelo lógico da Semana 03, estruturado em 3FN. Os scripts devem ser executados em uma base `academia_semana_03`; crie-a previamente com `CREATE DATABASE academia_semana_03;` e conecte-se a ela (PostgreSQL não oferece `CREATE DATABASE IF NOT EXISTS`). Execute `sql/01_schema.sql`, `sql/02_seed.sql`, `sql/03_transacoes.sql`, `sql/04_explain.sql` e, por último, `sql/05_acessos.sql` com uma conta administrativa.

## Estrutura e tipos

As tabelas `aluno`, `instrutor`, `plano`, `assinatura`, `aula` e `participa` preservam as entidades e relações fornecidas. `INTEGER GENERATED BY DEFAULT AS IDENTITY` substitui `AUTO_INCREMENT` e mantém IDs automáticos compatíveis com `RETURNING`. CPF permanece `CHAR(11)` com unicidade; e-mails são `VARCHAR(100)` com unicidade e validação básica de formato. Datas civis, como nascimento e início/fim de assinatura, usam `DATE`. O instante de cadastro usa `TIMESTAMPTZ` para armazenar com fuso horário. Valores monetários (não existentes no modelo original) não foram inventados.

Os status e meios de pagamento são `TEXT` limitados por `CHECK`, alternativa explícita e fácil de evoluir ao `ENUM` do MySQL. `NOT NULL`, `UNIQUE`, `CHECK`, `DEFAULT`, PK e FK documentam e protegem as regras. A associação aluno-aula usa PK composta, impedindo matrícula duplicada.

## Índices

Índices únicos de CPF/e-mail e plano são criados pelas restrições `UNIQUE`. Índices adicionais em `assinatura(id_aluno)`, `assinatura(id_plano)`, `aula(id_instrutor)` e `participa(id_aula)` aceleram junções e buscas pelas FKs. A PK de `participa(id_aluno,id_aula)` também atende consultas que começam pelo aluno. Índices em colunas FK não são criados automaticamente pelo PostgreSQL. Não se duplicam índices das PKs e chaves únicas.

## Transações

`03_transacoes.sql` contém duas transações multi-tabela. Ambas usam `BEGIN`, `SAVEPOINT`, `RETURNING`, `COMMIT` e uma ramificação comentada de `ROLLBACK` para demonstrar reversão. `RETURNING` captura os IDs gerados e `currval`/IDs fixos não são necessários. Para observar o rollback, descomente a alternativa indicada e não execute o `COMMIT` daquela transação.

## EXPLAIN ANALYZE

`04_explain.sql` analisa duas consultas de junção alinhadas às consultas do modelo lógico. O plano depende do volume e estatísticas: em tabelas pequenas, o otimizador pode escolher `Seq Scan`, mesmo havendo índice, pois isso custa menos que percorrer o índice. Com os três registros da carga de exemplo, isso é esperado; `ANALYZE` atualiza estatísticas. Para uma demonstração realista, repita a carga com mais dados representativos. O critério de avaliação é verificar o plano observado, não presumir que índice será sempre escolhido.

## Controle de acesso

`05_acessos.sql` deve ser executado por administrador. Cria a role sem login `academia_leitura`, um usuário leitor associado com apenas `SELECT`, e um usuário de operação com leitura e escrita nas tabelas do schema `public`. Nenhum deles recebe privilégios de criação de objetos; `REVOKE` remove privilégios públicos amplos no schema e nas tabelas. Substitua as senhas exemplo antes de uso real. Para conceder acesso futuro às novas tabelas, aplique `ALTER DEFAULT PRIVILEGES` como o mesmo proprietário que as criará.
